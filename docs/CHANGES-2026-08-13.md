# ZMK Architecture Upgrade & Bluetooth Fix (2026-08-13)

This document explains what changed in this pass over the Lotus58 BLE ZMK
config, why, and what to watch out for.

## TL;DR

- **Found and fixed the Bluetooth bug**: the right-hand board's `defconfig`
  set `CONFIG_BOARD_LOTUS58_BLE_LEFT=y` instead of
  `CONFIG_BOARD_LOTUS58_BLE_RIGHT=y`. That made the right half build as a
  second **central** device instead of a **peripheral**, which breaks BLE
  split pairing (two centrals can't form a split link, and the right half
  would never behave as a normal peripheral half towards a host).
- Migrated the board definition from ZMK's old (pre-Zephyr-4.1) board layout
  to the current **Hardware Model V2** layout, and moved it from the
  deprecated `config/boards` mechanism to a proper Zephyr module under
  `boards/`.
- Pinned `west.yml` to ZMK `main` (Zephyr 4.1) instead of the old `v0.3` tag,
  and updated both GitHub Actions workflows to match.

## 1. The Bluetooth bug

File: `config/boards/arm/lotus58_ble/lotus58_ble_right_defconfig` (old path)

```diff
- CONFIG_BOARD_LOTUS58_BLE_LEFT=y
+ CONFIG_BOARD_LOTUS58_BLE_RIGHT=y
```

`Kconfig.defconfig` only sets `CONFIG_ZMK_SPLIT_ROLE_CENTRAL=y` inside the
`if BOARD_LOTUS58_BLE_LEFT` block. Because the right board's defconfig forced
`BOARD_LOTUS58_BLE_LEFT=y` as well as the automatically-selected
`BOARD_LOTUS58_BLE_RIGHT=y`, the right-hand firmware ended up with **both**
board symbols set, and therefore also became a split-central. Two
simultaneously-central halves cannot establish a working split BLE link, and
the "right" half would also try to advertise as a standalone central to
hosts. This is the most likely explanation for the reported Bluetooth
problems and has been fixed as part of the migration (the corresponding new
file is `boards/tweetydabird/lotus58_ble/lotus58_ble_right_defconfig`, which
no longer sets any `BOARD_*` symbol at all — see below for why that's now
correct).

**Action for you:** flash both halves with the newly built firmware and
re-pair (reset both halves within a few seconds of each other, as usual for
ZMK split pairing). If Bluetooth still misbehaves after this, it's worth
double-checking that both a full "left" and full "right" firmware image were
actually flashed to the correct physical half — the symptoms of the old bug
are similar to a left/right image swap.

## 2. Move to ZMK Hardware Model V2 (Zephyr 4.1)

ZMK's `main` branch moved to Zephyr 4.1 in December 2025
([blog post](https://zmk.dev/blog/2025/12/09/zephyr-4-1)), which introduces a
new **Hardware Model V2 (HWMv2)** for boards. All out-of-tree boards (like
this one) must be migrated by hand — an automatic upgrade script exists but
explicitly does **not** support split keyboards.

What changed, mirroring how ZMK's own in-tree split boards (e.g. the
MoErgo Glove80) are structured today:

| Old (HWMv1, `config/boards/arm/lotus58_ble/`) | New (HWMv2, `boards/tweetydabird/lotus58_ble/`) |
| --- | --- |
| `boards/arm/<board>/...` (arch-named parent dir) | `boards/<vendor>/<board>/...` (vendor-named parent dir) |
| `Kconfig.board` with `bool` + `depends on SOC_...` | Split into `Kconfig.lotus58_ble_left` / `Kconfig.lotus58_ble_right`, each `select`-ing the SoC and `ZMK_BOARD_COMPAT` |
| `<board>_defconfig` selecting `CONFIG_SOC_*` / `CONFIG_BOARD_*` | Those selects removed — HWMv2 does this automatically from `board.yml` |
| No `board.yml` | New `board.yml` declaring both left/right boards and their SoC (`nrf52840`) |

Key new file: `boards/tweetydabird/lotus58_ble/board.yml`

```yaml
boards:
  - name: lotus58_ble_left
    vendor: tweetydabird
    socs:
      - name: nrf52840
  - name: lotus58_ble_right
    vendor: tweetydabird
    socs:
      - name: nrf52840
```

Most ZMK boards now require an explicit `zmk` board variant on the build
target (e.g. `nice60/nrf52840/zmk`). That variant only exists for a board if
its `board.yml` declares `variants: [{name: zmk}]` under the SoC entry — and
if it does, the board's devicetree/defconfig files must also be split into
per-variant files named `<board>_<soc>_<variant>.dts` /
`_<soc>_<variant>_defconfig`. This board follows the same (simpler)
pattern ZMK's own Glove80 uses instead: `Kconfig.lotus58_ble_left` /
`Kconfig.lotus58_ble_right` `select ZMK_BOARD_COMPAT` unconditionally
(instead of conditionally on a variant symbol), `board.yml` declares no
variants, and the plain board name is used as the build target — no `zmk`
suffix needed or accepted. `build.yaml`:

```yaml
include:
  - board: lotus58_ble_left
    artifact-name: lotus58_ble_left
  - board: lotus58_ble_right
    artifact-name: lotus58_ble_right
```

The devicetree (`.dtsi`/`.dts`), pinctrl, keymap and Kconfig option content
itself did **not** need to change — the charlieplex kscan driver
(`zmk,kscan-gpio-charlieplex`), the battery driver
(`zmk,battery-nrf-vddh`), and the matrix-transform/physical-layout bindings
are all unchanged in current ZMK.

## 3. Moved off the deprecated `config/boards` mechanism

The **old** layout put the board files inside `config/boards/arm/...`. That
directory is scanned by a legacy fallback in ZMK's build system
(`app/keymap-module/modules/modules.cmake`) which explicitly logs:

> `The 'config/boards' folder is deprecated. Please use a module instead.`

This fallback is why the board could still be found and built despite
`zephyr/module.yml` (which declares this whole repo as a proper Zephyr
module with `board_root: .`) pointing at a `boards/` folder that, before this
change, didn't actually exist at the repository root.

The board files now live at `boards/tweetydabird/lotus58_ble/` (repository
root), which is what `zephyr/module.yml`'s `board_root: .` actually expects,
and this is the officially supported, non-deprecated mechanism.

**Follow-up fix after the first CI run failed** ("No board named
'lotus58_ble_left' found"): it turned out `zephyr/module.yml` had never
actually been committed to this repository at all. `.gitignore` had a
blanket `zephyr/` rule (intended to keep the real Zephyr RTOS checkout that
`west update` creates locally out of git), which also silently excluded our
own hand-written `zephyr/module.yml`. It only ever existed as an untracked
file on one machine's disk — so on GitHub, ZMK's build workflow never saw
it, never passed `-DZMK_EXTRA_MODULES=...`, and `boards/` was invisible to
the build. `.gitignore` now excludes `zephyr/*` but explicitly keeps
`zephyr/module.yml` tracked. If your Bluetooth or build problems ever
resurface after future changes, `git ls-files zephyr` is a quick way to
confirm this file is actually committed.

## 4. `west.yml`: tracking `main` instead of `v0.3`

```diff
- revision: v0.3
+ revision: main
```

`v0.3` is ZMK's latest tagged release, but it still uses the pre-4.1,
pre-HWMv2 architecture — i.e. it's the *old* architecture, not the new one.
The HWMv2 changes and all recent driver/feature work only exist on `main`
right now; ZMK's own docs call `main` the "tester" channel and explicitly
recommend pinning to a release once you just want stability
([pinning blog post](https://zmk.dev/blog/2025/06/20/pinned-zmk)). Since the
goal here was explicitly "newest architecture, all current features", this
config now tracks `main`. **Trade-off to be aware of:** `main` can have
occasional breaking changes; if a future build breaks unexpectedly, that's
the first thing to check, and re-pinning to a release tag (once ZMK ships a
Zephyr-4.1-based `v0.4`) is a one-line fix in `config/west.yml` and
`.github/workflows/build.yml`.

## 5. GitHub Actions workflows

- `.github/workflows/build.yml`: now calls
  `zmkfirmware/zmk/.github/workflows/build-user-config.yml@main` (was
  `@v0.3`), matching the `west.yml` change above.
- `.github/workflows/release.yml`: the previous version manually reimplemented
  the west workflow with `west init` (no arguments — this doesn't work
  without either `-l <path>` or `-m <url>`) and then copied `boards/` and
  `zephyr/` into a `zmk/` checkout that doesn't exist at that point in the
  script. On top of that, the manual `west init -l config` approach has a
  structural problem for this repo specifically: our own
  `zephyr/module.yml` lives at the repository root in a directory literally
  named `zephyr`, which is also the exact path `west update` would use to
  check out the real Zephyr RTOS — a hard collision. This is why ZMK's
  official reusable workflow always builds in an isolated temp directory
  when it detects a `zephyr/module.yml` in the repo. The release workflow
  now reuses that same official reusable workflow (as a workflow job) and
  just adds a second job that downloads the built artifacts, renames them
  with the release tag, and publishes a GitHub Release — instead of
  re-implementing (and getting wrong) the underlying west/CMake plumbing.

## 6. Metadata files (`lotus58_ble.zmk.yml`, `lotus58_ble.yaml`)

- Fixed a typo: `sibllings:` → `siblings:` (the old key wasn't a field the
  schema recognizes, so the sibling relationship between the left/right
  boards was silently not being recorded).
- Removed `display`, `encoder`, `underglow`, `backlight` from the declared
  `features:` list. None of these are actually wired up by default in this
  board's devicetree/Kconfig — the nice!view display SPI pins and the
  rotary encoder nodes are present but explicitly commented out as
  unverified/needs-adjustment, and there is no RGB or PWM backlight hardware
  defined anywhere in the board files. Advertising features that aren't
  actually enabled is misleading for anyone using ZMK's keyboard picker
  tooling. If you do wire up a nice!view display or an encoder later, re-add
  the corresponding feature and finish/verify the commented-out devicetree
  nodes in `lotus58_ble.dtsi`.

## Not changed / explicitly out of scope

- **ZMK Studio** was not enabled. Studio support requires physical key
  position data (`keys` property) on the `zmk,physical-layout` node, which
  needs real PCB coordinates that weren't available here. The existing
  matrix-transform-only physical layout still builds and works fine for
  normal keymap use; adding Studio support is a good follow-up if you have
  (or want to measure) the physical key layout of the PCB.
- The commented-out rotary encoder and nice!view display support were left
  as-is (still commented out) — they were already unverified/"may need
  adjustment" before this change, and enabling them blind without hardware
  to test against would risk introducing new, hard-to-diagnose bugs.
